# Calendar — руководство для агентов

Перед началом любой задачи прочитай этот файл, проверь `git status --short` и не откатывай чужие незавершённые изменения.

## Проект

- Calendar — школьный календарь мероприятий на Node.js ESM, Express и Handlebars.
- Точка входа: `app.js`; представления: `views`; клиентский код и стили: `public`; MySQL-пул: `vendor/db.mjs`.
- Репозиторий ведётся только в `https://github.com/teyhd/Calendar.git`. Не добавляй и не используй прежний репозиторий-источник как remote.
- Сохраняй существующую архитектуру: маршруты и бизнес-логика находятся в `app.js`, шаблоны — в `views`, клиентские сценарии — в `public/js`.

## Среда и credential values

- До работы с данными прочитай `vendor/db.mjs`, актуальные переменные окружения и существующие запросы/миграции. Не подменяй их предположениями.
- Calendar использует `DB_HOST`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `DB_PORT`, `SESSION_SECRET`, `NODE_ENV` и `PORT`. Не переноси в него несовместимые имена переменных из Attendance (`MDBHOST`, `DBUSER`, `DBPASS`, `DBNAMESUSR`).
- Секреты, приватные ключи и production-доступы хранятся только в `.env`, окружении процесса или игнорируемом `AGENTS.local.md`. Не читай без необходимости, не выводи, не коммить и не публикуй их значения.
- В production параметры БД и `SESSION_SECRET` задаются через окружение PM2/сервиса либо локальный `.env`, но никогда не tracked-файлами, логами, issue, commit message или Markdown-документацией.
- Используй operational credential values только для Calendar и только когда это необходимо для поставленной задачи.
- Если секретный файл оказался tracked, не удаляй его молча: остановись, сообщи пользователю и предложи безопасный план очистки истории и замены секрета.

## База данных и границы данных

- Все запросы выполняй через существующий пул `vendor/db.mjs`; сохраняй параметризацию SQL и существующие проверки доступа.
- Перед изменением схемы найди источник истины для таблиц и согласуй миграционный подход. В репозитории сейчас нет отслеживаемой схемы/миграций БД — не создавай таблицы или поля наугад.
- Не выполняй `DROP`, массовые `DELETE`/`UPDATE`, очистку таблиц и другие destructive SQL-операции без прямого запроса, точного scope и понятного rollback-плана.
- Для изменений, затрагивающих несколько таблиц, применяй транзакцию там, где частичное выполнение нарушит целостность данных.
- Если Calendar подключается к SSO или общим школьным справочникам, считай их внешним read-only контуром: не пиши в `sso.*`, `school_local.sso_users` и `school_local.sso_kafs`, не меняй их схему миграциями и не создавай локальные дубли классов/учеников без явной потребности.
- Локальные таблицы Calendar (`events`, `event_approvals`, `event_participants`, `notifications` и связанные сущности) изменяй только в рамках их бизнес-правил и с проверкой прав пользователя.

## Проверка

- Установка: `npm install`.
- Локальный запуск: `npm start`; dev-режим: `npm run dev`.
- Скрипт `npm test` в исходном проекте является placeholder и намеренно завершается ошибкой; не считай это успешной проверкой.
- Для изменений UI проверь основной пользовательский сценарий в браузере, когда это применимо.

## Git, merge и ANET-деплой

Каждое изменение завершается следующим циклом:

1. Работай в отдельной короткоживущей ветке и сделай сфокусированный коммит без секретов и несвязанных файлов.
2. Проверь изменение в объёме, соответствующем риску.
3. Влей ветку в `main` (`git checkout main`, затем `git merge <feature-branch>`). Деплоится только результат в `main`.
4. Отправь `main` в `origin` — единственный remote `teyhd/Calendar`.
5. Разверни именно этот commit на ANET. Производственные доступы, адрес сервера и секретные команды держи только в игнорируемом `AGENTS.local.md`.
6. Перед деплоем проверь фактическую схему запуска на ANET: `pm2`, `systemd`, cron или ручной Node-процесс. После деплоя проверь процесс, HTTP-ответ основного сценария и свежие runtime-логи.

Не деплой незамёрженные ветки, не изменяй production без необходимости и не добавляй `AGENTS.local.md` в Git.

## Уведомления и отчёт

- После каждой завершённой задачи отправляй через `notify` краткий результат пользователям `99` и `100`, без секретов и лишнего текста.
- В финальном отчёте укажи, что изменено, что проверено, hash задеплоенного commit и оставшиеся риски.
